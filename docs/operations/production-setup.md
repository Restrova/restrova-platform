# Production Setup Guide

How to run Restrova in production. The platform targets (Render with a
persistent disk, Railway/Docker with a mounted volume) already provide HTTPS at
their edge; the application needs **no TLS code of its own**.

## 1. Deployment shapes that work out of the box

- **Render** (`render.yaml` / `render.persistent.yaml`): web service + 1 GB
  disk mounted at `/var/data`, `DATABASE_PATH=/var/data/restaurant.db`,
  `JWT_SECRET` generated by the platform, health check on `/api/health`.
  Render terminates TLS automatically — no app-side HTTPS config needed.
- **Docker / Railway** (`05-devops-qa/Dockerfile`, `railway.json`):
  non-root user, `VOLUME /data`, `DATABASE_PATH=/data/restaurant.db`,
  health check on `/api/health`. Put a TLS-terminating proxy or platform edge
  in front; the app already sets `trust proxy` in production so client IPs and
  rate limiting work correctly behind it.

## 2. Required environment variables (production)

| Variable        | Required                                   | Production value / rule                                                                                                                                                                              |
| --------------- | ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `NODE_ENV`      | yes                                        | `production`                                                                                                                                                                                         |
| `JWT_SECRET`    | yes                                        | Strong random value ≥ 32 chars. The server **refuses to start** with a missing/placeholder secret. Generate: `node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"`              |
| `DATABASE_PATH` | yes                                        | Durable storage path (e.g. `/var/data/restaurant.db`). The server **refuses to start** if it is missing or points at `/tmp`-style temporary storage.                                                 |
| `CLIENT_ORIGIN` | yes when the frontend is served separately | Comma-separated allowed browser origins (e.g. `https://app.example.com`). On Render/Railway the platform hostname is allowed automatically via `RENDER_EXTERNAL_HOSTNAME` / `RAILWAY_PUBLIC_DOMAIN`. |

### Strongly recommended

| Variable                 | Default            | Notes                                                                                                                             |
| ------------------------ | ------------------ | --------------------------------------------------------------------------------------------------------------------------------- |
| `ENABLE_DEMO_SEED`       | _(empty)_          | **Never set in production.** The demo restaurant (owner@harbor.test) is only created on explicit opt-in. Tests set it themselves. |
| `BACKUP_ENABLED`         | `false`            | Set `true` to enable the daily backup scheduler — see `backup-restore.md`.                                                        |
| `BACKUP_DIR`             | `<db dir>/backups` | Keep on the same durable disk.                                                                                                    |
| `BACKUP_INTERVAL_HOURS`  | `24`               | Lower for tighter RPO.                                                                                                            |
| `BACKUP_RETENTION_COUNT` | `7`                | How many newest backups to keep.                                                                                                  |
| `OPENAI_API_KEY`         | _(empty)_          | See §5 — without it the assistant runs in deterministic demo mode and the server logs `ai_demo_mode_in_production` at startup.    |

### Optional tuning (defaults are sane)

| Variable                                                                                       | Default                  | Notes                                                            |
| ---------------------------------------------------------------------------------------------- | ------------------------ | ---------------------------------------------------------------- |
| `PORT`                                                                                         | `4000`                   | Render/Docker set their own.                                     |
| `BCRYPT_COST`                                                                                  | `12`                     | Must be ≥ 12 in production (enforced).                           |
| `REQUEST_BODY_LIMIT`                                                                           | `3mb`                    | JSON body limit.                                                 |
| `JWT_EXPIRES_IN`                                                                               | `12h`                    | Token lifetime; logout invalidates earlier (server-side cutoff). |
| `API_RATE_LIMIT_MAX`                                                                           | `300`                    | See §4.                                                          |
| `AUTH_RATE_LIMIT_MAX`                                                                          | `20`                     | See §4.                                                          |
| `RATE_LIMIT_WINDOW_MS`                                                                         | `900000` (15 min)        | Shared window for all limiters.                                  |
| `OPENAI_MODEL`, `OPENAI_MAX_OUTPUT_TOKENS`, `OPENAI_REASONING_EFFORT`, `OPENAI_TEXT_VERBOSITY` | `gpt-5.6`, `1600`, — , — | Only used when `OPENAI_API_KEY` is set.                          |

Import limits (`IMPORT_MAX_*`, `IMPORT_PREVIEW_ROWS`,
`IMPORT_CONFIRMATION_TOKEN_TTL_SECONDS`, `IMPORT_PREVIEW_RATE_LIMIT_MAX`,
`IMPORT_ACTION_RATE_LIMIT_MAX`) keep the staged-import pipeline safe; see
`docs/imports/README.md`.

## 3. HTTPS / reverse proxy

Nothing to configure inside the application:

- TLS is terminated by the platform (Render/Railway) or your proxy.
- `trust proxy` is enabled automatically when `NODE_ENV=production`, so
  `req.ip` and rate limiting see the real client IP from `X-Forwarded-For`.
- Helmet sets HSTS and `upgrade-insecure-requests` in production.
- Do **not** add app-side TLS code or a second proxy hop — that is
  platform-owned.

## 4. Rate limits (current values and how to tune)

All limiters share one 15-minute window (`RATE_LIMIT_WINDOW_MS`) and key by
client (user id once authenticated, IP before that), normalized per endpoint so
rotating resource ids cannot multiply a budget. Exceeded requests get `429`
with `RateLimit-Limit` / `RateLimit-Remaining` / `RateLimit-Reset` headers.

| Limiter        | Default budget        | Applies to                                                                              |
| -------------- | --------------------- | --------------------------------------------------------------------------------------- |
| API (global)   | 300 requests / 15 min | every `/api` endpoint, including health probes (platform checks are well within budget) |
| Auth           | 20 requests / 15 min  | `/api/auth/login`, `/api/auth/register` (per IP)                                        |
| Import preview | 20 / 15 min           | `/api/data/import/preview`                                                              |
| Import actions | 60 / 15 min           | import confirm/cancel/mapping endpoints                                                 |

Normal usage: a dashboard session makes single-digit API calls; chatting
heavily stays far below 300; a person logs in once. The one caveat: many staff
sharing one NAT IP each logging in during shift start — 20 logins / 15 min
covers ~20 people; raise `AUTH_RATE_LIMIT_MAX` (e.g. 50) if a single office
exceeds that. Protection against credential stuffing stays intact either way.

## 5. OpenAI vs demo mode

- **No API key is committed anywhere.** `.env` is git-ignored and ships empty;
  keys are provided only as environment variables on the backend service.
- With `OPENAI_API_KEY` set, the assistant calls the OpenAI Responses API
  (`OPENAI_MODEL`, default `gpt-5.6`) for real reasoning; tool calls still run
  against the restaurant's own data.
- Without a key the assistant runs the deterministic built-in demo engine. In
  production this is loudly logged at startup (`ai_demo_mode_in_production`) —
  it is a functional fallback, never a silent substitute for the LLM.
- The demo engine's known limitation: it does not solve arithmetic word
  problems (evals 92/106 — the 14 `restaurant_logic` cases). With a real key
  those are handled by the LLM. Do not "fix" this with hardcoded answers.

## 6. First deploy checklist

1. Provision the service with the required env vars above.
2. Verify `/api/health` → `{"status":"ok"}` and `/api/ready`.
3. Register a real account; confirm the demo restaurant is absent.
4. Set `BACKUP_ENABLED=true`, run `scripts/backup-db.js` once manually and
   execute the restore drill in `backup-restore.md`.
5. Walk through `production-checklist.md`.
